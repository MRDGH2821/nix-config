# Containerized self-hosted GitHub Actions runners

Research date: 2026-11-18. Scope: GitHub Actions on GitHub.com; check the corresponding GitHub Enterprise Server documentation for version-specific differences.

## Repository context

At the time of this research, `services.github-runners.runner1` ran as a NixOS service on the home-lab host and registered with the AxisNexa organization, using the `gh-runner1` SOPS secret. That service configuration has since been removed. The host enables Podman and its Docker-compatible socket in [`podman.nix`](../nix/modules/nixos/features/podman.nix). The workflows in this repository currently select `ubuntu-latest`, so they use GitHub-hosted runners rather than this self-hosted runner. The separate [Forgejo runner plan](superpowers/plans/2026-07-17-forgejo-runner-service.md) does not establish GitHub runner compatibility.

## Options and support

- GitHub allows a self-hosted runner to run in a container; its runner application must run on a supported operating system and architecture, reach GitHub, and have sufficient resources. A runner container and the job's optional container are separate concerns. [GitHub: self-hosted runners](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners), [requirements](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#requirements-for-self-hosted-runner-machines), [job container customization](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/customize-containers).
- **Kubernetes:** Actions Runner Controller (ARC) is GitHub's recommended Kubernetes autoscaling solution and reference implementation of its scale-set APIs. GitHub maintains a minimal runner image, `ghcr.io/actions/actions-runner`; a custom ARC image must meet its documented runner path and startup requirements. [GitHub: runner autoscaling](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#autoscaling), [ARC runner image](https://docs.github.com/en/actions/concepts/runners/actions-runner-controller#about-the-runner-container-image).
- **Custom orchestration:** GitHub's Runner Scale Set Client is a Go module for building custom autoscaling across containers, VMs, and other infrastructure. Alternatively, operators can build scaling automation using `workflow_job` webhooks and runner registration APIs; GitHub notes webhook delivery timing can affect reliability. These choices require operator-owned provisioning and cleanup. [GitHub: autoscaling](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#autoscaling).
- **Support boundary:** GitHub supports only the latest ARC Autoscaling Runner Sets release; legacy ARC is community supported. Cluster administration, template customization, and several integrations are outside GitHub Support's scope. [GitHub: ARC support](https://docs.github.com/en/actions/concepts/runners/support-for-arc).

## Lifecycle and operations

- GitHub recommends ephemeral runners for autoscaling. Register with `config.sh --ephemeral`; GitHub assigns at most one job and deregisters the runner after it processes the job. The operator must arrange to wipe the execution environment after deregistration. JIT runners, created through the REST API, also run at most one job. [GitHub: ephemeral runners](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#ephemeral-runners-for-autoscaling), [removing runners](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/remove-runners).
- Deregistration alone does not clean reused hardware or shared state. GitHub recommends forwarding ephemeral runner diagnostic logs to external storage and warns that reusing hardware can expose prior-job information. Clean workspaces, volumes, caches, and any shared execution infrastructure as part of the design. [GitHub: ephemeral runner logs](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#ephemeral-runners-for-autoscaling), [JIT runner security](https://docs.github.com/en/actions/reference/security/secure-use#using-just-in-time-runners).
- A runner needs outbound HTTPS access on port 443 to GitHub's required domains. GitHub documents runner auto-update behavior and notes that ephemeral container images may repeatedly update; if updates are disabled, maintain the image and follow GitHub's update requirements. [GitHub: communication and updates](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#communication), [runner software updates](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#runner-software-updates-on-self-hosted-runners).
- If no matching runner is available, the job stays queued and fails after 24 hours; a job assigned to a runner that does not pick it up within 60 seconds is requeued. An offline ephemeral runner is removed after more than one day without connecting. [GitHub: routing](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#routing-precedence-for-self-hosted-runners), [removal](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/remove-runners).

## Docker and Podman

- For the ordinary Docker-backed runner path, GitHub requires Linux and Docker for Docker container actions and service containers; the runner account must be able to access the Docker service. Container jobs also require a suitable container execution backend. [GitHub: runner requirements](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#requirements-for-self-hosted-runner-machines), [Docker troubleshooting](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/monitor-and-troubleshoot#troubleshooting-containers-in-self-hosted-runners), [job containers](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/run-jobs-in-a-container).
- ARC's documented container modes for container jobs, services, and container actions are `dind` and `kubernetes`. Docker-in-Docker requires privileged mode, including GitHub's documented rootless image alternative. Kubernetes mode uses container hooks and Kubernetes resources; GitHub warns that allowing jobs without a job container in Kubernetes mode can expose elevated Kubernetes API privileges. [GitHub: ARC container modes](https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/deploy-runner-scale-sets#using-docker-in-docker-or-kubernetes-mode-for-containers).
- GitHub documents Linux-only container customization hooks, currently in public preview, which can implement job-container management using Podman; root access is not required by the hook interface. This is a custom integration to implement and validate, not a statement that an unmodified Docker-backed runner is officially supported with Podman substituted. [GitHub: customizing containers](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/customize-containers).
- Podman's API exposes a Docker compatibility layer, but that fact alone does not prove every GitHub runner workflow or action works with it. Test the specific job containers, service networking, actions, mounts, permissions, and image builds required by the intended workloads. This is an inference from [Podman's API documentation](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html) and [GitHub's Docker requirement](https://docs.github.com/en/actions/reference/runners/self-hosted-runners#requirements-for-self-hosted-runner-machines).

## Security implications

- GitHub recommends self-hosted runners only for private repositories and warns that untrusted pull request code can compromise the runner; private and internal repositories also require care with users able to submit workflows or pull requests. Use runner groups and repository access controls, least-privilege workflow tokens, and restrict secrets. [GitHub: adding runners](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners), [secure use](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners).
- Access to a rootful Docker daemon is highly privileged: Docker warns that daemon access can grant root access to the host. Podman states that its API grants full Podman functionality and arbitrary code execution as the service user; rootless confines that authority to the service user's privileges, not to an individual job. Treat either socket as a sensitive credential, including when mounted into a runner container. [Docker: daemon socket security](https://docs.docker.com/reference/cli/dockerd/#daemon-socket-option), [Podman: API security](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html#security).
- GitHub recommends separating ARC runner pods from operator pods by namespace and isolating production workloads from arbitrary workflow code. A disposable runner container does not by itself isolate a shared host socket, persisted data, network services, or Kubernetes credentials; that conclusion follows from the documented daemon and cluster privileges. [GitHub: ARC deployment](https://docs.github.com/en/actions/how-tos/manage-runners/use-actions-runner-controller/deploy-runner-scale-sets#deploying-a-runner-scale-set), [Docker daemon security](https://docs.docker.com/engine/security/), [Podman API security](https://docs.podman.io/en/latest/markdown/podman-system-service.1.html#security).

## Practical direction for this repository

For a homelab without Kubernetes, evaluate a custom disposable runner and an explicit provisioning/cleanup mechanism before choosing a runtime. If workflows need GitHub's standard container features, Docker on Linux is the documented baseline; use Podman hooks only after testing the preview integration against the actual workflows. Keep execution isolated from homelab services and credentials, and preserve logs outside the disposable environment. These are design recommendations based on the sources above, not a claim that the existing Forgejo service is a GitHub runner.

A practical first implementation would:

1. Build and pin a runner image with a registration/startup script; verify the chosen image supports standalone registration because GitHub's maintained image is documented for ARC.
2. Run a supervisor under systemd that obtains short-lived registration or JIT configuration using a credential protected by SOPS, starts one Podman runner container, and creates a fresh runner after each completed job. Never bake credentials into the image.
3. Register each runner as ephemeral, use a disposable workspace, remove the container and its writable storage after the job, and forward diagnostic logs before cleanup. Handle startup failures, stale registrations, and image updates.
4. Start with trusted private repositories and jobs that do not need Docker, without mounting the host Podman socket. Restrict runner-group access and network access to homelab services. Test container actions separately before enabling a container backend.
5. If jobs execute untrusted code or need strong separation from other homelab services, put the runner and its container runtime inside a disposable VM; a Podman container shares the host kernel and is not equivalent to a VM.

This is a proposed design, not an implementation or a guarantee that Podman will support every workflow. Registration credentials, runner group, provisioning lifecycle, and workload requirements must be settled before deployment.
